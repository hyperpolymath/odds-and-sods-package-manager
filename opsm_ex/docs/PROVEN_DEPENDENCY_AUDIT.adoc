Date: 2026-03-10

=== Overview

OPSM depends on the `+proven+` library (vendored at
`+opsm_ex/deps/proven/+`) for formally verified safety primitives. This
library is an Idris 2 project with dependent types and totality
checking.

The `+proven+` codebase contains approximately 4,577 references to
`+believe_me+` across 44 source files. The vast majority of these are
`+PROOF_TODO+` comments marking where `+believe_me+` is used or needs to
be replaced. The actual `+believe_me+` calls number in the hundreds,
spread across FFI stubs, axiomatised lemmas, and incomplete proofs.

This audit focuses on the `+believe_me+` instances in the ECHIDNA
soundness proofs, which are the subset most relevant to OPSM’s trust
pipeline.

=== ECHIDNA Soundness Proofs

==== Location

`+src/Proven/ECHIDNA/Soundness.idr+` – lines 165-185

==== What It Assumes

The `+consensusSoundness+` function proves that if N provers all agree
on a proof, then the proof is valid under all their proof theories. The
function is implemented by structural induction over the list of
provers.

The base case (empty list) is correctly proved. The inductive case (line
185) uses `+believe_me+`:

[source,idris]
----
consensusSoundness {provers = (p :: ps)} proof (AllAgree proof (eq :: rest)) =
  believe_me (ValidProof proof) :: consensusSoundness proof (AllAgree proof rest)
----

This `+believe_me+` skips the actual proof that
`+proverSound p proof eq+` produces a `+ProofValid proof+` with the
right type for the `+All+` list. The comment on line 159 explains:
"`This is axiomatised as it follows directly from proverSound applied at
each list element.`"

==== Risk Assessment

[width="100%",cols="25%,38%,14%,23%",options="header",]
|===
|Location |What is assumed |Risk |Severity
|`+Soundness.idr:185+` |`+proverSound p proof eq+` produces
`+ProofValid proof+` for the head of the prover list, coerced via
`+believe_me+` |*LOW* |The assumption is mathematically correct –
`+proverSound+` is an interface method that by definition produces
`+ProofValid proof+` from `+verify p proof = True+`. The `+believe_me+`
here is working around an Idris 2 limitation with interface resolution
inside `+All+` constraints, not making an unsound assumption.
|===

*Assessment: REASONABLE.* The `+believe_me+` in `+consensusSoundness+`
is a proof engineering shortcut, not a soundness hole. The core
single-prover soundness theorem (`+echidnaSoundness+`) is fully proved.
The multi-prover consensus is an extension that is logically sound but
not formally verified due to Idris 2’s difficulty resolving interface
constraints inside the `+All+` higher-order type.

=== Broader believe_me Landscape (Non-ECHIDNA)

The remaining `+believe_me+` instances fall into these categories:

==== 1. FFI Boundary Stubs (LOW risk, ~40% of instances)

Files like `+SafeCrypto.idr+`, `+SafeDigest.idr+`, `+SafeDateTime.idr+`,
`+SafeCapability.idr+`, `+SafeCSV.idr+`, `+SafeLRU.idr+`,
`+SafeSet.idr+`, `+SafeRegistry.idr+`, `+SafeJson/Parser.idr+`.

These use `+believe_me+` at FFI boundaries where Idris cannot verify
properties of external (Zig/C) code. This is standard practice and
expected.

*Risk to OPSM:* LOW. FFI stubs are validated by the Zig layer and Idris
type signatures constrain inputs/outputs.

==== 2. Proof Stubs (PROOF_TODO markers) (MEDIUM risk, ~50% of instances)

Files with large blocks of
`+PROOF_TODO: Replace believe_me with actual proof+`: -
`+SafeHistory.idr+` (2 actual believe_me, 36 PROOF_TODO comments) -
`+SafePassword/Proofs.idr+` (406+ references) - `+SafePath/Proofs.idr+`
(368+ references) - `+SafeCrypto/Proofs.idr+` (285+ references) -
`+SafeUrl/Proofs.idr+` (266+ references) - `+SafeRegex/Proofs.idr+`
(250+ references) - `+SafeEmail/Proofs.idr+` (252+ references) -
`+SafeBase64/Proofs.idr+` (189+ references) - `+SafeJson/Proofs.idr+`
(198+ references) - `+SafeFiniteField.idr+` (252+ references) -
`+SafeString/Proofs.idr+` (133+ references) - And others

These are proofs that should be filled in but currently use
`+believe_me+`. The PROOF_TODO comments make the intent clear.

*Risk to OPSM:* MEDIUM. OPSM uses proven’s SafeCrypto, SafeJson,
SafeUrl, and SafeString modules. If the axiomatised proofs are wrong,
type safety guarantees in those modules are weakened.

==== 3. Complex Inductive Proofs (LOW-MEDIUM risk, ~10% of instances)

Proofs involving list operations (`+pushBounded+`, `+popRedoIdentity+`
in SafeHistory) where the proof obligation is clear but Idris 2’s
elaborator needs help.

*Risk to OPSM:* LOW. These are bounded-collection proofs that are
morally correct but not mechanically verified.

=== Recommended Upstream Fixes

[arabic]
. *ECHIDNA `+consensusSoundness+` (Priority: LOW):* Replace the
`+believe_me+` with an actual proof using `+proverSound+` and manual
`+All+` construction. This may require restructuring the `+Consensus+`
type to carry the evidence in a more inference-friendly way.
. *SafeCrypto/Proofs.idr (Priority: HIGH for OPSM):* These proofs
underpin OPSM’s cryptographic verification. Fill in the `+believe_me+`
instances or at minimum add property-based tests covering the assumed
invariants.
. *SafeUrl/Proofs.idr (Priority: HIGH for OPSM):* URL validation is
security-critical for OPSM’s registry adapters. The 266 believe_me
references in URL proofs should be prioritised.
. *SafeJson/Proofs.idr (Priority: MEDIUM for OPSM):* JSON parsing
correctness affects all registry API responses.
. *SafePassword/Proofs.idr (Priority: LOW for OPSM):* OPSM uses its own
Erlang-based password/crypto stack, not proven’s.

=== Mitigation Strategies for OPSM

[arabic]
. *Defense in depth:* OPSM does not rely solely on proven’s type-level
guarantees. The `+Opsm.Verified.Http+`, `+Opsm.Verified.Json+`, and
`+Opsm.Verified.Url+` modules provide runtime validation independent of
proven’s proofs.
. *Property-based testing:* OPSM’s own test suite (`+opsm_ex/test/+`)
includes property tests (`+imp_property_test.exs+`,
`+verified/url_property_test.exs+`, `+verified/json_property_test.exs+`,
`+verified/result_property_test.exs+`) that exercise the same invariants
proven claims to verify.
. *Classical crypto fallback:* The PQ trust pipeline (`+pq_trust.ex+`,
`+hybrid_signatures.ex+`) uses Ed25519 from Erlang/OTP’s `+:crypto+`
module as a baseline. Post-quantum signatures via the NIF are additive
security, not a replacement.
. *Pin proven version:* Do not upgrade the proven dependency without
re-auditing. The current vendored version’s believe_me landscape is
documented here.
. *Monitor upstream:* Track the proven repository for PROOF_TODO
resolution. When proofs are filled in, update the vendored copy and
re-audit.

=== Summary

[cols=",,",options="header",]
|===
|Category |Count (approx) |Risk to OPSM
|ECHIDNA soundness |1 believe_me + 18 PROOF_TODO |LOW
|FFI boundary stubs |~40% of total |LOW
|Proof stubs (PROOF_TODO) |~50% of total |MEDIUM
|Complex inductive proofs |~10% of total |LOW-MEDIUM
|===

The ECHIDNA soundness `+believe_me+` is mathematically reasonable and
not a practical concern. The higher-risk items are the proof stubs in
SafeCrypto, SafeUrl, and SafeJson, which OPSM mitigates through
independent runtime validation and property-based testing.
