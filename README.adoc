= odds-and-sods-package-manager (opsm)

A federated, multi-language package manager with formal verification, a multi-dimensional trust pipeline, automated ecosystem health monitoring, and agentic package discovery for obscure languages.

**Now supports:** npm, Crates.io, Hex, PyPI, Nimble (Nim), Idris2, and any git-based package ecosystem. Includes HAR integration for agentic discovery of packages from legacy sites, university repos, and unmaintained projects.

== Supported Ecosystems

**Centralized Registries** (HTTP API):
- **npm** (JavaScript/Node.js) - https://npmjs.com
- **Crates.io** (Rust) - https://crates.io
- **Hex** (Elixir/Erlang) - https://hex.pm
- **PyPI** (Python) - https://pypi.org
- **Nimble** (Nim) - https://nimble.directory

**Git-Based** (Decentralized):
- **Idris2** - Curated packages + agentic discovery
- **Any git repository** - Generic git adapter for languages without registries

**Agentic Discovery** (via HAR):
- Legacy project sites, university repositories, FTP servers
- Automated GitHub/GitLab search across all languages
- Web scraping for unmaintained packages
- Interactive user assistance when automation fails

See `docs/adding-language-adapters.adoc` for adding new languages.

== Scope

opsm wires together the hyperpolymath ecosystem into a single user-facing CLI and federation hub.

- Verification & logic: `proven` (Idris2)
- Trust pipeline: `checky-monkey`, `claim-forge`, `palimpsest-license`, `oikos`
- Manifests & ingestion: `nickel-config-reporter`, `hybrid-automation-router`, `protocol-squisher`, `scaffoldia`
- Registry & federation: `cicd-hyper-a`, `http-capability-gateway`, `git-private-farm`, Radicle, IPFS
- Bot ecosystem: `rhodibot`, `seambot`, `echidnabot`, `robot-repo-automaton`

== Federation architecture

Primary hub (opsm-registry-hub) mirrors to GitHub/GitLab/Codeberg/corp.io/uni.edu plus Radicle P2P, with event propagation for:

- package-published
- security-advisory (critical, immediate, notify dependents)
- deprecation-notice
- maintainer-change
- compatibility-break

== Quick start

[source,bash]
----
# Build ReScript
deno task build

# Run directly
deno task opsm status

# Or install globally
deno install --allow-read --allow-env --allow-net --allow-run -n opsm cli/Main.res.js

# Then use
opsm publish ./my-package
opsm audit @scope/package
opsm status
----

== Verified code via proven

opsm uses the https://github.com/hyperpolymath/proven[proven] library for mathematically verified operations:

- **SafeUrl** - URL validation for service configurations
- **SafeJson** - Safe JSON parsing for API responses
- **Result type** - Crash-free error handling

All critical path operations use formally verified code from proven's Idris 2 core.

== Manifest ingestion pipeline

Before `opsm publish` hits the trust pipeline the CLI now:

1. **Locates and validates** the manifest via Nickel when `nickel-config-reporter` is installed (`nickel-config-reporter validate ...`).
2. **Normalizes** the manifest through `opsm.Imp`, emitting the IMP payload described in `docs/imp/imp.schema.json`.
3. **Stages** the IMP JSON for HAR by writing `/tmp/opsm-har-ingest/<package>.imp.json`, so HAR can route the normalized manifest through its agents.

This keeps the publish flow aligned with the documented Nickel + HAR pipeline even before every service is online.

== Minimal http-capability-gateway API

`opsm.RegistryGateway` now exposes a tiny HTTP surface that mirrors the `http-capability-gateway` story:

* `POST /packages/publish` accepts `{ "manifest": <manifest>, "imp": <imp>, "digest": "sha256:..." }` and records the package in memory for downstream consumers while the HAR queue keeps the federation path fed.
* `GET /packages/:name` returns the stored manifest, IMP payload, digest, and `published_at`.
* The server listens on port `4050` by default and responds with JSON; every successful ingest automatically publishes through this gateway so the HTTP API stays in sync with the staged IMP files.

== Seam analysis helper

Run `mix run scripts/seam_analysis.exs` to ingest several synthetic manifests against the CLI and registry gateway, verifying the HAR staging files and gateway responses while printing timing metrics and digests. This provides the “hardcore seam” trace you asked for without needing to manually craft manifests.
